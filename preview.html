Why it exists

Most budgeting tools are built for one person. This one is built for a workspace.

Shared money is a coordination problem. Budgetary gives every household or team a private home for the numbers, then makes the shared parts obvious: who spent what, how the month is tracking, and who is allowed to change it.

For the person who tracks it

Add an expense in seconds, search it later, and see the whole month on one dashboard. No spreadsheet formulas, no reconciliation rituals.

For the people who share it

Invite a partner or teammate with their own login. Owners, admins, members and viewers each see exactly the controls they should.

For the data behind it

Each workspace is isolated by PostgreSQL row-level security — enforced by the database, proven by tests, invisible to the people using it.

Budgets that speak human

A budget is one monthly limit, an alert threshold and a pace line. On day 19 of 31, the app shows what you should have spent by now — and exactly how far ahead or behind you are.

  • On-track, approaching and over-budget states
  • Alert threshold per workspace
  • Undo a mistyped limit from the toast

Reports without the spreadsheet

Monthly and yearly views break spending down by category, compare income with expenses across six months, and export a clean CSV. The math happens in SQL; the browser only formats it.

  • Category shares and budget performance
  • Six-month trend with readable axes
  • Formula-injection-safe CSV export

One workspace, many people

Invite by link, choose a role, revoke a pending invite. Each person gets their own login and sees the same workspace through the permissions you gave them. Owners can’t be removed; nobody can change their own role.

  • Separate logins, one shared budget
  • Viewer role is read-only in UI and API
  • Invite tokens are single-use and email-bound

Bring your history with you

Built to be trusted

Isolation is a database rule, not a promise in a README.

Forced RLS

Every tenant table is protected by row-level security. A non-superuser app role and per-transaction tenant context close the gaps application code forgets.

Rotating sessions

Short-lived access tokens live in memory. Refresh tokens rotate, are hashed at rest, travel in HttpOnly cookies, and revoke their family on reuse.

Fair-use limits

A sliding window is keyed per tenant when authenticated, per IP otherwise. Credential endpoints get a stricter budget and a clear 429.

Audit trail

Logins, money changes, imports, category creation, invites and branding updates are appended per tenant — the story of who changed what.

Under the hood

A small number of boundaries, held consistently.

The interface is approachable. The path underneath it is deliberately boring: one guarded request pipeline, one tenant boundary, one source of financial truth.

1. EdgeCaddy terminates TLS, sets HSTS, forwards to the app.
2. Webnginx serves the React SPA and proxies /api.
3. APIFastAPI authenticates, rate-limits and pins the tenant.
4. DataPostgreSQL enforces RLS row by row, even on a missed filter.

Every tenant transaction starts with set_config('app.current_tenant_id', …). Money is NUMERIC(14,2), aggregated in SQL and formatted only at the edge. Access tokens last 15 minutes; refresh tokens rotate. The rate limiter is in-process — one API replica by default, or move it to Redis before scaling out.

Questions

The things people ask before they run it.

Do I need any cloud accounts or API keys?

No. Docker Compose starts PostgreSQL, the API, the web app and an edge proxy. There are no external analytics, AI calls or payment services in the stack.

How exactly is one workspace kept out of another?

Tenant tables use PostgreSQL row-level security, forced for the application role. Each request pins the current tenant inside its transaction, and the app connects as a non-superuser. Cross-tenant reads return 404 or empty sets, and the isolation suite probes this directly, including raw SQL.

Can a partner or teammate have their own login?

Yes. Owners and admins create an invite link with a role; the invited person registers with that link and their own email. The invite is single-use and bound to the email address.

What do the four roles actually allow?

Owners and admins manage workspace settings and members. Members manage money data. Viewers can read everything but every write path is disabled in the UI and rejected by the API. The owner cannot be removed or re-roled.

What happens if I import the same file twice?

With “skip duplicates” on (the default), rows matching an existing transaction — same kind, date, amount and note — are counted as skipped instead of inserted. The result view shows added, skipped and failed counts.

Can each workspace use a different currency and language?

Yes. Currency, locale and timezone are per workspace and are stored with the tenant. Amounts are stored as exact decimals and formatted in the browser, so switching from dollars to euros changes presentation, not the underlying records.

Is this production-ready?

It is a hardened, self-hosted build with tested isolation, rotating sessions, per-tenant rate limits, TLS at the edge and CI. Before real use, change every secret, set ENVIRONMENT=production, run one API replica (or move the limiter to Redis) and back up the database volume.

Why is there also a Python CLI?

cli/budget_system.py is a dependency-free tutorial version of the same idea. It is a gentle way to read plain classes and menus before exploring the full SaaS.
